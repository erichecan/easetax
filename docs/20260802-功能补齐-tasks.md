## P0 · 阻断真实使用

- [x] **T1 复核页抬头字段可编辑**
      验收：复核页能改供应商/发票号/账单日/到期日/小计/税额/总额并落库；改完后 CRA 凭证等级随之重算；`synced` 后只读
      产出：`api/documents/[id]/extraction/route.ts`、`components/doc-header-editor.tsx`
      实测：无 token 401 · synced 改抬头 409 · 非法金额/日期 400 · 空 body 400 ·
            **填入 GST 号后凭证等级 incomplete → ok（重算生效）** · 审计留 before 值

- [x] **T2 复核页加行 / 删行**
      验收：能新增一行（描述+金额+科目+税码）、能删除一行；行合计与票面总额不符时显式提示差额；确认时校验仍生效
      产出：`api/documents/[id]/lines/route.ts`、`review-workbench.tsx`
      实测：401 无 token · 空描述/非法金额/不存在科目 400 · **跨单据删行 404（越权保护）** ·
            synced 加行 409 · 差额提示实显「行合计 $490 与票面小计 $999 差 $509（少了，可能漏行）」

- [x] **T3 税码 semanticKey 指认界面**
      验收：客户设置页能为每个 QBO 税码指认用途（标准可抵扣/餐饮50%/不可抵扣/无税/不用）；指认后重跑单据税码不再留空；未指认时页面明确警示「税码规则无法生效」
      产出：`api/clients/[id]/tax-codes/route.ts`、`components/tax-code-mapper.tsx`
      实测：401 · 未知用途 400 · **同一用途指给两个税码 400（防映射二义性）** ·
            跨客户税码 400 · 清空/恢复指认 200 · 清空餐饮 50% 后页面实显
            「税码规则当前无法生效：还有 餐饮 50% 抵扣 没有对应税码…相应行的税码留空、全部转人工」

- [x] **T4 银行流水 CSV 导入**
      验收：对账页能上传 CSV（日期/摘要/金额三列，容忍列名差异与 BOM）；导入后立即参与匹配；重复导入不产生重复流水；解析失败逐行报错不中断
      产出：`lib/bank-csv.ts`+15 项测试、`api/clients/[id]/bank-txns/route.ts`、`reconciliation.tsx`
      实测：401 · 首次导入 3 笔（收入行跳过、坏行逐行报错「第 5 行：日期无法解析」）·
            **重复导入 imported:0 duplicates:3** · 表头不对报出实际表头 ·
            导入后 3 笔立即出现在缺收据清单（9 笔）
      覆盖：RFC4180 引号/BOM/CRLF、ISO 与 mm-dd-yyyy 与 dd-MMM-yyyy、括号负数、
            借贷分列、中文表头、零金额行

- [x] **T5 客户 CRUD**
      验收：客户列表「+ 新增客户」可用（名称/行业/省份/税号），建成后 `inboundEmail` 按契约 §4.3 派生；重名校验；新客户立即出现在侧边栏
      产出：`api/clients/route.ts`、`components/new-client-dialog.tsx`
      实测：401 · 空名称/非法省份 400 · **重名 409** · 创建返回派生的
            inboundEmail=client-client_xxx@inbound.easetax.ca · 新客户即时出现在列表与侧边栏
      教训：路径含括号导致 sed 静默失败，且在错误目录跑 tsc 得到假通过 —— 验证必须在 apps/web 下跑

- [x] **T6 邮件入站 webhook**
      验收：`POST /api/inbound/email` 接收带附件的入站邮件，HMAC 签名校验（无效签名 401）；按收件地址解析出 clientId；附件走与上传同一条 pipeline；非白名单类型跳过并记审计
      产出：`api/inbound/email/route.ts`、`lib/inbound-email.ts`+12 项测试
      实测：无签名/错签名 401 · 外域地址 400 · 不存在客户 404 · 无附件返回 note 并记审计 ·
            **真实 jpg 附件（MIME 谎报 octet-stream）按扩展名兜回 image/jpeg 并入库，source=email** ·
            同封邮件里的 .exe 被跳过并记入审计 · 未配密钥时端点返回 503 而非裸奔
      注：入库后状态 ocr_failed 属预期 —— Veryfi 试用到期，恰好证明走的是真实 pipeline

- [x] **T7 OCR 失败重试 + 退避**
      验收：OCR 抛错后自动重试至多 3 次、指数退避；仅对可重试错误（网络/5xx/429）重试，4xx 立即失败；重试次数写入审计
      产出：`lib/retry.ts`+9 项测试、`pipeline/ingest.ts`
      实测：**前两次 503 后成功 → needs_review**，审计留 `ocr:recovered_after_retry`
            含每次退避时长；**403 试用到期只调 1 次**（不浪费额度）；持续 500 试满 3 次
      退避序列：454 → 815 → 1945 → 3520 → 6600ms（抖动只向下，不突破 max）
      修了个真 bug：抖动原本可能向上突破 max 上限（attempt=10 算出 8400 > 8000），测试抓到

## P1 · 影响可用性

- [x] **T8 退回（reject）**
      验收：复核页「退回」按钮可用，需填原因；状态走 `needs_review → rejected`；退回后不再出现在待复核；审计留原因
      产出：`api/documents/[id]/reject/route.ts`、`review-workbench.tsx`
      实测：401 · 不填原因 400 · synced 退回 409 · **rejected 后重复退回 409（终态）** ·
            退回后状态分布 needs_review 减 1、rejected=1，归入「异常待处理」不再占用 ④ 复核
            审计：`status:needs_review->rejected {"reason":"重复件，与 INV-88231 相同"}`

- [x] **T9 人工匹配 / 取消匹配**
      验收：对账页每笔流水可手动关联某张单据、可标记「无需收据」、可撤销；`matchStatus` 落 `manual|ignored`；人工裁决优先于自动匹配（契约 §4.6）

      产出：`scripts/verify-qbo.ts`（`npm run verify:qbo`）、`.env.example`（补

      **已完成的准备（commit `608167d`）**：

        每客户一个 URL，而 Intuit 要求 redirect_uri 与门户登记值**精确匹配**、登记又是

        超长号复跑仍命中去重。连跑两次结果一致（幂等）。
      - 🐛 **实测抓到真 bug 并已修**：QBO `DocNumber` 上限 **21 字符**（超了报 code 2050
        ValidationFault）。发票号来自 OCR，长过 21 的真实存在，原样传过去就是会计师
        看不懂的 400。已在 provider 层截断（保留**尾部**——截头部会把只差尾号的两张
        发票混成一张，去重误判），且查重与建单**共用同一个截断值**（分开算的话查重
        查完整号必然查不到，去重直接失效）。5 项新单测 + 脚本第 8/9 步覆盖。
      - 🐛 **同时堵掉一个会让 app 掉线的隐患**：脚本与 app 共用同一个 refresh token，
        Intuit 会轮换它；只更新 `.env` 不更新库，库里那个就作废，表现为「app 莫名
        丢了 QBO 连接」。脚本现在轮换时一并加密回写数据库并明说改了什么。

      ⚠️ **未覆盖：加拿大税**。沙箱是美国公司，税码只有 `TAX/NON/California/Tucson`，
